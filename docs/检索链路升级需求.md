# 检索链路升级需求

**文档状态：** 待实施
**创建日期：** 2026-09-17
**参考：** [Tencent/WeKnora](https://github.com/Tencent/WeKnora) 的 RAG 主链路（`internal/types/chat_manage.go` 中的 `rag_stream`）
**关联：** [业务场景设计.md](业务场景设计.md) 三、P1-7「混合检索」的展开

---

## 一、背景与对照

WeKnora `rag_stream` 流水线：

```
LOAD_HISTORY → QUERY_UNDERSTAND → CHUNK_SEARCH_PARALLEL → CHUNK_RERANK → CHUNK_MERGE → FILTER_TOP_K → … → CHAT_COMPLETION_STREAM
```

WorkPilot 当前链路：

```
anonymize ∥ classify_intent → sync → rewrite(串在 retrieve 内) → 纯向量检索(LIMIT 5 → Python 阈值过滤) → decide_tool ⇄ execute_tool → generate
```

| WeKnora 阶段 | WorkPilot 现状 | 差距 |
|---|---|---|
| QUERY_UNDERSTAND（一次调用输出改写 + 意图） | 意图分类与查询改写是两次独立 LLM 调用 | 可合并，但非必须 |
| CHUNK_SEARCH_PARALLEL（向量 ∥ 关键词） | 仅向量 | **缺关键词检索与融合** |
| 向量检索：候选扩展 → 阈值 → TopK，`SET LOCAL hnsw.*` | `LIMIT 5` 后在 Python 里按阈值过滤，被滤掉的名额不补位 | **结构性问题** |
| CHUNK_RERANK（模型重排 + 综合分 + MMR） | 无 | 效果优化，需评测证明收益 |
| CHUNK_MERGE（去重、相邻块合并、短块补邻居） | 无 | 成本低、收益明确 |
| 文档级权限过滤 | 四级可见性在 SQL 内过滤 | WeKnora 没有，是本项目差异点，保留 |

另外在核对代码时确认了一个与 WeKnora 无关但必须先修的问题：**原文外发路径不止一条**（见 R0）。

---

## 二、评估结论

| 建议项 | 结论 | 说明 |
|---|---|---|
| 脱敏移到 `llm_client` 出口统一处理 | **采纳，优先级最高** | 安全问题，且当前有 5 条路径绕过脱敏 |
| 改写 + 分类合并为一次调用 | 采纳，放在 R0 之后 | 省一次 LLM 调用；7B 模型 JSON 输出需降级方案 |
| 候选扩展 → 阈值 → TopK；`SET LOCAL hnsw.ef_search / iterative_scan` | **采纳** | 改动小；`iterative_scan` 对权限过滤严格的用户（`dept_only`）尤其重要 |
| `visibility` / `dept_id` 冗余到 embeddings 表 | **暂不采纳** | 权限可变更，冗余引入一致性维护；先 `EXPLAIN ANALYZE`，有证据再做 |
| 混合检索 + RRF 融合 | **采纳** | RRF 只用排名，不依赖分数量纲 |
| 关键词侧换 ParadeDB 镜像（pg_search BM25） | **不采纳** | 需 PG16 → PG17 迁移，且违反架构约束「标准 Postgres + pgvector」；RRF 只用排名，`ts_rank` 排序足够 |
| 重排（bge-reranker） | 采纳，但后置 | 需要本地推理 sidecar，收益必须用评测证明 |
| 相邻块合并 / 短块补邻居 | **采纳** | 分块已带 `heading` / `page_no` / `chunk_index`，实现成本低 |
| Wiki / 沙箱 / 技能 / IM / 多模型接入 / GraphRAG / 事件链 | 不采纳 | 与本项目目标无关；LangGraph 图已是事件链的等价物 |

## 三、需求清单

### R0 · 脱敏收口到 LLM 出口（安全，P0）

**现状：** `anonymize_node` 只产出 `anonymized_query`，仅 `llm_query_for_completion()` 一处使用。以下调用把原文送到了 LLM：

| 调用点 | 外发内容 | 位置 |
|---|---|---|
| `classify_intent_node` | 原始 query | `graph/nodes.py` |
| `generate_chitchat_node` | 原始 query | `graph/nodes.py` |
| `generate_answer_node` | 最近 6 条原始历史 | `graph/nodes.py` |
| `decide_tool_node` | 最近 4 条原始历史 | `graph/nodes.py` |
| `_rewrite_query` | 原始 query + 最近 4 条原始历史，且 `user_role=None` 绕过分档判断 | `graph/nodes.py` |

本地 Ollama 不出网时无害；一旦 `LLM_PROVIDER=openai_compatible` 或管理员分档命中外部模型，这五条路径全部泄漏。

**目标：** 所有发往外部 LLM 的消息（system / user / assistant / 历史）在 `llm_client` 的 `chat_complete` / `chat_stream` 出口处统一脱敏；节点层不再各自判断。

**实现要点：**
- `llm_client` 在 `resolve_provider() == "openai_compatible"` 时，对 `messages[*].content` 逐条应用 `_PII_RULES`；本地 Ollama 不处理
- `_PII_RULES` 从 `nodes.py` 移到独立模块（如 `core/anonymizer.py`），节点和 `llm_client` 共用
- `anonymize_node` 与 `llm_query_for_completion()` 可删除或退化为 trace 记录用（保留 `anonymized_query` 便于在 trace 里看到出网内容）
- 数据库仍存原文（审计需要），只改出口
- `_rewrite_query` 的 `user_role=None` 改为传真实角色
- 系统提示中拼入的检索片段（`【参考资料】`）同样经过出口脱敏——文档里也可能含手机号

**边界：** 脱敏后 LLM 可能在工具参数里回传占位符（如 `"phone": "[手机号]"`），`execute_tool_node` 应把含占位符的参数视为无效并走"必填参数缺失"路径。

**验收：**
- 单元测试：mock 外部 provider，断言五条路径的出网 messages 均不含手机号 / 邮箱 / 密钥
- 单元测试：本地 provider 时 messages 保持原文
- trace 中记录 `anonymized=true/false` 与出网 provider

### R1 · 查询理解合并（P1）

**现状：** `classify_intent`（与 anonymize 并行）和 `_rewrite_query`（在 retrieve 内串行）是两次 LLM 调用；分类不看历史，改写才看。

**目标：** 一次调用输出 `{"rewrite_query": "...", "intent": "rag|chitchat"}`，历史同时服务于两者。

**实现要点：**
- 新节点 `query_understand`，替代 `classify_intent` + `_rewrite_query`；R0 完成后无需再与 anonymize 并行
- 正则快速通道保留：命中明显闲聊时不调 LLM
- 无历史时 prompt 只要求分类，`rewrite_query` 原样返回
- JSON 解析失败降级：`intent` 走关键词匹配，`rewrite_query` 用原 query
- 改写结果只用于检索 embedding；生成阶段仍用用户原话（避免改写偏差进入答案）
- trace 记录改写前后文本

**验收：**
- 多轮追问 golden case（见第四节）通过率不低于合并前
- 单轮 RAG 请求的 LLM 调用次数从 2 降为 1

---

### R2 · 向量检索结构修正（P0，改动小）

**现状：** `retriever.py` 先 `LIMIT :top_k`（5）再在 Python 里按 `min_score` 过滤，被过滤的名额不补位；权限严格的用户容易拿到 0-2 条结果。

**目标：** 候选扩展 → 阈值 → TopK，与 WeKnora `VectorRetrieve` 结构一致。

**实现要点：**
- SQL 改为子查询：内层 `WHERE 权限 ORDER BY distance LIMIT :candidate_k`（`candidate_k = clamp(top_k × 20, 50, 200)`），外层 `WHERE score >= :min_score ORDER BY score DESC LIMIT :top_k`
- 事务内 `SET LOCAL hnsw.ef_search = <candidate_k>` 与 `SET LOCAL hnsw.iterative_scan = strict_order`；后者需 pgvector ≥ 0.8，不支持时捕获异常降级
- `iterative_scan` 的价值：HNSW 是先取近邻再套 WHERE，`dept_only` / `specific_users` 这类过滤严格的用户，默认 `ef_search=40` 的候选可能被过滤到几乎为空；迭代扫描会继续往外找直到凑够
- `EXPLAIN ANALYZE` 确认走 `embeddings` 上的 HNSW 索引；把结果写进本文档附录，作为"是否需要冗余权限字段到 embeddings 表"的决策依据
- `top_k` / `min_score` / `candidate_k` 提升为 `config.yaml` 可配置

**验收：**
- 集成测试：构造 100 个 chunk，其中仅 3 个对某 `dept_only` 用户可见，断言该用户能检索到全部 3 个
- 权限受限用户的 golden case（见第四节）`doc_hit_rate` 不低于改前

### R3 · 混合检索 + RRF 融合（P1）

**现状：** 纯向量；条款编号、单号、专有名词（"TR-2026-0091"、"第 3.2 条"、"nomic-embed-text"）这类查询向量召回差。

**目标：** 向量 ∥ 关键词并行检索，RRF 融合后取 TopK；权限过滤两路各自在 SQL 内完成。

**实现要点：**

关键词侧（不引入新镜像）：
- `doc_chunks` 新增 `content_tsv tsvector` 列 + GIN 索引（迁移 0004）
- 分词在应用层用 jieba（`jieba.lcut_for_search`），以空格拼接后 `to_tsvector('simple', ...)` 写入；查询同样分词后 `to_tsquery('simple', 'a | b | c')`
- 排序用 `ts_rank_cd`；分数只用于排名，不参与融合
- 文档入库、重新索引时同步写 `content_tsv`；提供一次性回填脚本
- 为什么不用 BM25 / ParadeDB：RRF 只消费排名，`ts_rank` 的排序质量对于万级 chunk 足够；避免更换数据库发行版和 PG 大版本迁移

融合：
```python
def rrf(vec_ids, kw_ids, k=60, wv=0.7, wk=0.3):
    score = {}
    for w, ranked in ((wv, vec_ids), (wk, kw_ids)):
        for rank, cid in enumerate(ranked, 1):
            score[cid] = score.get(cid, 0.0) + w / (k + rank)
    return sorted(score, key=score.get, reverse=True)
```
- `k` / 权重可配置；默认沿用 WeKnora（60 / 0.7 / 0.3）
- 两路各取 `candidate_k` 候选，融合后取 `top_k`
- 向量侧仍保留 `min_score` 阈值；关键词侧无阈值（排名靠后自然被截断）
- sources 里的 `score` 字段改为 RRF 分，或同时保留 `vec_score` / `kw_rank` 供 trace 排查
- 检索节点 trace 记录两路各命中数、融合后 TopK 来源分布

**验收：**
- 关键词类 golden case（见第四节）`doc_hit_rate` 明显高于纯向量
- 语义类 case 不退化（对比 R2 完成后的基线）
- 关键词侧单路故障（如 jieba 异常）时降级为纯向量，不报错

### R4 · 分块合并与上下文扩展（P1）

**现状：** 检索结果直接拼进 prompt；制度条款常被 800 字切断，命中的 chunk 只含条款上半段。

**目标：** 参考 WeKnora `merge.go`：去重 → 同文档相邻块合并 → 短块补邻居。

**实现要点：**
- 检索结果按 `(doc_id, chunk_index)` 去重
- 同一文档内 `chunk_index` 连续的命中块合并为一段，去掉 overlap 重复的前缀
- 命中块长度 < 阈值（如 200 字）时，取同文档前后各 1 块补上（需 `doc_chunks` 按 `(doc_id, chunk_index)` 查询，已有索引则直接用）
- 合并后总字符数不超过上下文预算（如 4000 字），超出时按 RRF 分从低到高丢弃
- 引用来源仍指向原命中 chunk（`chunk_id` / `heading` / `page_no` 不变）

**验收：**
- 单元测试覆盖：相邻合并、overlap 去重、短块补邻、预算截断
- 制度条款类 golden case 的答案完整性（LLM-as-judge 或人工抽查）提升

---

### R5 · 重排（P2，评测门控）

**现状：** 无。

**前提：** R3 完成且评测落库后，用数据判断是否需要。Ollama 无原生 rerank 接口，需要独立推理服务。

**实现要点（若做）：**
- 本地 sidecar：`bge-reranker-v2-m3` + 轻量 HTTP 服务，docker-compose 增加一个容器；或调用外部 rerank API（需经 R0 脱敏）
- 参考 WeKnora `rerank.go`：清洗（去 Markdown / URL）→ 综合分 `0.6 × 模型分 + 0.3 × 检索分 + 0.1 × 来源权重` → 阈值过滤 → MMR 去冗余（Jaccard）
- 融合后取 `candidate_k`（如 20）送重排，输出 `top_k`
- 重排失败 / 超时降级为 RRF 排序

**验收：** 与 R3 基线对比，`doc_hit_rate` 或答案质量指标有可量化提升，否则不合入。

## 四、评测先行

动手前补充 golden case，分三组，每组不少于 5 条，标注期望命中的 `doc_id`：

| 组 | 验证对象 | 示例 |
|---|---|---|
| 多轮追问 | R1 | 先问"报销住宿上限是多少"，再问"那出差补贴呢" / "病假呢" / "上面说的审批人是谁" |
| 权限受限用户 | R2 | 客服部员工问只有研发可见的文档；`specific_users` 白名单外的员工提问 |
| 关键词 / 编号查询 | R3 | "第 3.2 条说了什么"、"TR-2026-0091 是什么单"、"nomic-embed-text 是哪个模型" |

每完成一项（R0 → R2 → R1 → R3 → R4）跑一次评测并记录：`intent_acc`、`doc_hit_rate`、`recall@5`、平均检索耗时。评测结果落库（业务场景设计 P1-5）应在 R3 之前完成，否则无法对比。

## 五、实施顺序

| 顺序 | 需求 | 理由 |
|---|---|---|
| 1 | R0 脱敏收口 | 安全问题，改动集中在 `llm_client`，半天 |
| 2 | R2 向量检索结构修正 | 改动小，直接提升权限受限用户的召回 |
| 3 | 第四节 golden case + 评测落库 | 后续每步都要有对照 |
| 4 | R1 查询理解合并 | 省一次 LLM 调用，顺手把改写纳入 trace |
| 5 | R3 混合检索 | 需要迁移 + 回填，1–2 天 |
| 6 | R4 分块合并 | 纯代码，半天 |
| 7 | R5 重排 | 视 R3 后的评测数据决定 |
