## 二、业务场景

### 场景 A：报销申请智能预审与提交（主场景）✅ 已实现

#### 选择理由

系统已有报销制度文档和报销额度工具，员工使用频率高；该场景天然需要 **RAG（制度）+ 工具（数据）+ 多步推理（算超标）+ 槽位收集（缺信息追问）+ 人工确认（提交）+ 审批流（管理员）+ 审计**，能把 Agent 的各项能力串成一条完整链路。

#### 用户故事

> 员工张三：我上周去上海出差 3 天，酒店花了 1800，想报一下。

#### 目标对话流程（已实测跑通）

```
用户: 我上周去上海出差3天，酒店花了1800，想报销
Agent: [检索《差旅报销管理办法》]
       [调用 precheck_reimbursement(category=差旅住宿, amount=1800, days=3)]
       预审结果：
       - 住宿日均 600 元，超出你职级（senior）标准 500 元/天，超标 300 元
         📎《差旅报销管理办法》第 3.2 条
       - 年度住宿额度剩余 37,700 元，本次可覆盖
       - 超标部分需部门负责人特批
       SSE: form_incomplete → 还需要补充：出差起止日期
用户: 9月20号到22号，审批单 TR-2026-0100
Agent: [precheck → submit_reimbursement_request，幂等]
       已生成草稿 RB-20260916-0002，请确认提交
       SSE: confirm_required → 前端确认卡（金额/日期/超标说明）
用户: 点击「确认提交」
       POST /api/reimbursements/{id}/confirm → status=pending
rdadmin: 管理后台「报销审批」→ 批准 / 驳回
```

#### 涉及能力

| 能力 | 说明 | 状态 |
|---|---|---|
| 制度 + 数据双轨校验 | 规则在文档与结构化表，LLM 不做算术 | ✅ |

| 审批流 | 管理后台「报销审批」，部门管理员仅本部门；批准/驳回 + 意见 | ✅ |

## 五、设计决策说明

| 决策 | 理由 | 实现备注 |
|---|---|---|
| 用 pgvector 而不用独立向量库 | 权限过滤在同一条 SQL 内完成 | 已落地 |
| LLM 不做数值校验 | `precheck_reimbursement` 纯代码算超标 | 已落地 |
| 写操作三层防护 | 人工确认 + 前端确认卡 + 幂等键 | 确认用 draft API，非 interrupt |
| 脱敏不进检索 | 语义偏移影响召回；仅外部 LLM 前脱敏 | 已落地 + 热加载 |
| 节点级 trace | 出错按节点定位 | `agent_traces` |
| 评测结果落库 | 两次运行可 diff | 未做（P1） |
| 多轮检索用查询改写 | 改写后 embedding，失败降级 | 已落地 |
| 知识库持续改进 | 反馈→缺口→补文档→回归 | 表已有，页面未做 |
