### A.1 架构设计原则

本系统架构基于以下原则设计：

- **私有化优先**：所有业务数据不出内网，外部 LLM API 调用须经脱敏处理
- **组件最小化**：优先复用已有组件（如 pgvector 替代独立向量库），降低运维复杂度
- **容器化交付**：全部服务通过 Docker Compose 编排，一键部署，环境一致
- **渐进式扩展**：初期单机部署，架构预留水平扩展接口，不做过度设计

### A.7 架构关键决策说明

以下决策在设计阶段经过评估确认，记录于此供后续开发参考。

---

**决策一：pgvector 替代独立向量数据库**

向量数据与结构化数据（文档元信息、权限配置）存于同一 PostgreSQL 实例。权限过滤可在同一 SQL 查询中完成，无需跨库联合查询。当前文档规模（百份级）pgvector 性能完全满足需求，后续数据量增长至百万向量级别前无需替换。

---

**决策二：Embedding 模型与推理模型同由 Ollama 托管**

文档向量化（上传时）与查询向量化（检索时）必须使用**同一个 Embedding 模型**，否则两者向量空间不一致，相似度计算失效。统一由 Ollama 管理，模型切换时需同步重新向量化所有文档。

---

**决策三：APScheduler 使用 PostgreSQLJobStore 防重复执行**

Gunicorn 多 Worker 模式下，每个 Worker 进程独立初始化，若 APScheduler 直接内存调度，定时任务会被多个 Worker 同时触发。通过 `PostgreSQLJobStore` 将任务状态持久化至数据库，利用数据库行锁保证同一时刻只有一个 Worker 执行定时任务。

---

**决策四：Nginx 关闭 proxy_buffering 保障 SSE 实时性**

Nginx 默认会缓冲后端响应再转发给客户端。SSE 流式输出依赖逐 token 实时推送，若缓冲开启，用户会等待全部内容生成完毕后才一次性收到，流式效果完全失效。所有 `/api/*/stream` 路径须在 Nginx 配置中显式关闭 `proxy_buffering`，并将 `proxy_read_timeout` 设置为足够长（建议 300s）。

---

**决策五：仅 Nginx 端口对外暴露**

PostgreSQL（5432）、后端（8000）、Ollama（11434）、前端开发服务（3000）均不对宿主机外部暴露，所有流量统一经由 Nginx 入口。这一设计减少攻击面，同时便于统一管理 HTTPS 证书和访问日志。
