## 一、背景：当前基线为什么不可信

2026-09-18 的 42 case 全指标 1.0 是天花板效应，不是效果证明：

| 因素 | 现状 | 后果 |
|---|---|---|
| 语料规模 | 6 份文档（`test/*.md`） | 任何检索策略都能把全部文档召回 |
| `retrieval_top_k` | 8（`config.yaml`） | sources 按文档去重后几乎总是包含全部 6 份 |
| `doc_hit` 判定 | 期望标题出现在**任一** source（`eval/runner.py:207`） | 语料 6、返回 8 → 必然 1.0 |
| `citation_rate` 判定 | `len(sources) > 0` | 同上，必然 1.0 |
| 多轮 case | 0 条带 `conversation_history` | R1 查询改写完全未被评测 |
| 调参过程 | `must_include` 保底、修改 case 参数后达到 1.0 | 对着评测集调，评测集本身无区分度 |

结论：现有基线只能证明"链路没崩"，不能证明 R2–R4 任何一项有效。本文档的目标是让评测能区分好坏，然后**如实**记录数字。

## 二、需求

### E1 · 语料扩充（干扰文档）

**目标：** 25–30 份文档，使"命中正确那份"不再平凡。

| 类型 | 数量 | 说明 |
|---|---|---|
| 现有制度 | 6 | 保留 |
| 同主题干扰 | 每类 2–3 份，共 12–15 | 相近主题但答案不同：如《差旅报销管理办法（2024 旧版）》住宿上限 400、《销售部差旅补充规定》、《海外出差报销细则》 |
| 跨部门同名 | 3–4 | 不同 `dept_only` 的同名制度（研发/销售各一份《加班管理规定》），用于权限 + 检索双重验证 |
| 无关文档 | 4–5 | 与制度无关的长文（产品手册、会议纪要），占据向量空间 |
| 编号密集型 | 2 | 含大量条款编号、单号、专有名词的文档，用于关键词路验证 |

**实现要点：**
- 语料目录从顶层 `test/` 迁到 `backend/seed_docs/`，纳入 git；删除 `files.zip`
- `seed_demo.py` 按文件名前缀或 manifest（`seed_docs/manifest.json`：文件、visibility、dept、白名单）灌入
- 干扰文档的关键数字必须与正确文档**不同**，否则答案层面无法区分

**验收：** `seed_demo.py` 一次跑通，`documents` 表 ≥ 25 条 `ready`。

### E2 · 检索指标重定义

**现状：** `doc_hit` = 任一 source 命中；`top_k` = 8。

**目标：** 指标能反映排序质量。

| 指标 | 定义 | 说明 |
|---|---|---|
| `doc_hit@3` | 期望文档出现在 sources 前 3 | 替代现有 `doc_hit` |
| `recall@1` | 期望文档是 sources 第 1 | 新增 |
| `mrr` | 1 / 期望文档的排名，未命中为 0，全体平均 | 新增，对排序最敏感 |
| `heading_hit` | 期望 heading 出现在命中 chunk 的 `heading` 字段 | 新增，章节级；case 需标注 `expected_heading` |
| `citation_rate` | 保留，但仅统计 `should_cite` 且 `doc_hit@3` 为真的 case | 避免"引用了但引错"计为通过 |
| `permission_pass_rate` | 保留 | — |
| `intent_accuracy` / `tool_call_accuracy` | 保留 | — |

**实现要点：**
- `retrieval_top_k` 回到 5；评测与线上一致
- `eval_runs` 表增加新指标列；`case_results` 记录期望文档的实际排名（-1 为未命中）
- `expected_doc_title` 匹配改为精确文件名或 `doc_id`，不再用子串包含（"IT" 能匹配多份）
- case 文件里的中文字段确认 UTF-8 无 BOM（当前 `cases.json` 读出有乱码迹象，需核实）

**验收：** 新指标在 `POST /api/eval/run` 返回和 `eval_runs` 中可见；`GET /api/quality/runs` 对比页展示。

### E3 · case 扩充

**目标：** 从 42 条扩到 ≥ 70 条，按组标注，每组有明确验证对象。

| 组 | 数量 | 验证对象 | 要求 |
|---|---|---|---|
| 单轮制度问答 | 现有 | R2/R3 | 补 `expected_heading` |
| 多轮追问 | ≥ 8 | R1 改写 | 必须带 `conversation_history`（2–4 条）；追问本身无法独立检索，如"那病假呢""上面说的审批人是谁""改成 5 天呢" |
| 编号 / 专有名词 | ≥ 6 | R3 关键词路 | "第 3.2 条""TR-2026-0091""nomic-embed-text"；干扰文档中应有相似编号 |
| 干扰对照 | ≥ 8 | R2/R3 排序 | 问题在新旧版本 / 不同部门制度间有歧义，期望命中当前有效版本 |
| 权限负例 | 现有 + 4 | 权限过滤 | 跨部门同名制度：研发员工问"加班规定"应只命中研发版 |
| 工具 / 事务 | 现有 + 取消 + 幂等 | 场景 A/B | 补齐业务场景设计验收 6 |

**实现要点：**
- case 增加 `group` 字段；评测结果按组汇总，报告里每组单独一行
- 多轮 case 的 `conversation_history` 格式与 `RAGState.conversation_history` 一致
- `gap_to_eval` 导入的 case 自动打 `group: "gap"`，且 `expected_doc_title` 为空时不计入 `doc_hit@3` 分母（避免拉低指标或迫使填假值）

**验收：** 每组 ≥ 规定数量；评测报告按组输出。

### E4 · 对照实验与基线记录

**目标：** 用同一批 case 和语料，对比检索策略，把数字写进文档。

| 配置 | 开关 |
|---|---|
| 纯向量（R2 前结构） | `retrieval_enable_fts=false` + `candidate_k=top_k`（临时参数） |
| 向量候选扩展（R2） | `retrieval_enable_fts=false` |
| 混合 RRF（R3） | `retrieval_enable_fts=true`，`must_include` 关闭 |
| 混合 + must_include | 当前默认 |
| 混合 + 分块合并（R4） | 当前默认 |

**实现要点：**
- `must_include`、`merge` 各加配置开关（`retrieval_must_include`、`retrieval_merge_chunks`），便于对照
- `POST /api/eval/run` 接受 `label` 参数写入 `eval_runs.label`，区分实验
- 结果写入 [检索链路升级需求.md](检索链路升级需求.md) 附录「各阶段评测指标对照表」，格式：

| 配置 | doc_hit@3 | recall@1 | mrr | heading_hit | 关键词组 mrr | 多轮组 mrr | 平均检索 ms |
|---|---|---|---|---|---|---|---|

- **数字不到 1.0 是正常的，如实记录**；若某配置反而更差，也记录并在决策说明里写原因

**验收：** 对照表填满 5 行；据此决定 `must_include` 去留（见 E5）。

### E5 · `must_include` 去留决策

**现状：** 两路各 Top3 强制排最前（`retriever.py:342`），RRF 只决定这 6 条内部顺序，融合形同虚设。

**决策规则：**
- E4 对照中"混合 RRF"与"混合 + must_include"的 `mrr` 差异 < 0.02 → 删除 `must_include`，简化代码
- must_include 明显更好 → 改为**配额**实现：RRF 排序不动，仅保证关键词路至少 N 条（默认 2）进入 `top_k`，被挤出的按 RRF 顺序替换末位
- 无论哪种，`rrf_fuse()` 与内联实现合并为一处，权重从配置读取，文档同步
