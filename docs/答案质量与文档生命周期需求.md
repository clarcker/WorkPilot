## 二、需求

### Q1 · 文档生命周期（替代 P1-8「文档版本」）✅ 已实现

#### 问题

`documents.status` 只有 `processing / ready / failed / archived`，`archived` 是管理员归档（完全不召回）。企业制度实际有三种"活着但不该平等召回"的状态：现行、已被新版替代、草案。现在它们全是 `ready`。

#### 数据模型（已落地：migration 0009）

| 字段 | 类型 | 说明 |
|---|---|---|
| `documents.lifecycle` | enum `effective / superseded / draft` | 默认 `effective`；与 `status` 正交（`status` 管 pipeline，`lifecycle` 管业务） |
| `documents.effective_date` | date，可空 | 生效日期，展示与排序用 |
| `documents.supersedes_doc_id` | FK documents，可空 | 指向被本文档替代的旧版，形成版本链 |
| `seed_docs/manifest.json` | + `lifecycle`、`effective_date`、`supersedes` | seed 时按文件名建链 |

#### 行为

| 场景 | 行为 |
|---|---|
| 默认检索 | 只召回 `lifecycle = effective` |
| 用户明确问历史 | `query_understand` 输出增加 `time_scope: current / historical`；`historical` 时召回 `effective + superseded`，且 sources 标注「已被 vX 替代，现行版见 …」 |
| `draft` | 仅 `dept_admin` / `super_admin` 可召回；员工提问不召回也不透露存在（与权限过滤同一原则） |
| 上传同名文档 | 上传表单增加「作为新版本替代：<选旧文档>」；确认后旧文档 `lifecycle → superseded`，新文档 `supersedes_doc_id` 指向旧文档；旧文档 chunk / embedding 保留 |
| 管理后台 | 文档列表显示生命周期徽标；可手动切换 `effective ↔ superseded ↔ draft`；查看版本链 |
| 引用来源 | SourceCard 显示 `effective_date` 与生命周期徽标 |
| 审计 | 生命周期变更写 `audit_logs` |

#### 判定规则（`query_understand` prompt 增量）

"旧版 / 以前 / 原来 / 2024 年的 / 历史 / 修订前" → `historical`；其他一律 `current`。解析失败默认 `current`。

#### 评测

- `distractor` 组拆成两个子组打标：`distractor-lifecycle`（旧版 / 归档 / 草案）与 `distractor-topic`（海外出差细则、销售部补充规定、同名部门制度等**仍然现行**的干扰）
- 新增 `historical` 组 ≥ 4 条："2024 版住宿上限是多少""加班规定改过什么"——期望命中 superseded 文档
- 新增 `draft` 权限负例 ≥ 2 条：员工问病假医疗期，`forbidden_doc_title` = 征求意见稿

#### 验收

1. `distractor-lifecycle` 子组 mrr 提升；`distractor-topic` 子组**不允许因此变化**（它不受 lifecycle 影响，变化说明有别的东西动了）
2. `historical` 组 doc_hit@3 ≥ 0.75
3. 员工提问不出现 draft 文档；管理员提问可出现
4. 上传替代流程走通：旧版自动 superseded，版本链可在后台查看
5. 前后基线写入 [检索链路升级需求.md](检索链路升级需求.md) 附录

**这不是"把干扰文档排除掉让指标好看"**：`distractor-topic` 子组保留全部现行干扰，检索仍要靠 RRF 自己分辨；Q1 只解决业务上本就不该平等召回的那一类。

### Q2 · 多轮工具决策 ✅ 已实现

#### 问题

`decide_tool_node` 只看当前 query 与最近 4 条历史文本，不知道本会话已执行过哪些工具、结果是什么。用户追问"那剩余额度是多少"时会再次调用 `query_reimbursement_limit`，或在已生成草稿后再次 `submit`。

#### 需求（已落地）

- 状态增加 `session_tool_calls`：从 `tool_calls` 表按 `conversation_id` 取最近 N 次（工具名、参数摘要、结果摘要、时间）；`execute_tool` 非演练模式落库
- `decide_tool` prompt 增加「本会话已执行的工具」段落与规则：
  - 用户追问的是**已有结果**里的信息 → 不调用，用结果回答
  - 参数与上次相同 → 不调用（幂等结果可直接复用；代码侧 `_same_as_session_call` 兜底）
  - 用户明确要求重新查 / 参数变了 → 调用
- 已存在 `draft` 状态的报销申请时，再次 `submit` 直接返回该草稿的 `confirm_required`，不新建

#### 评测

`multiturn` 组补 ≥ 4 条带工具历史的 case：`conversation_history` 里含一次工具调用及结果，追问结果，`expected_tool: null`。

#### 验收

`multiturn` 组 `tool_call_accuracy` 不低于单轮组；新增 4 条全部通过。

### Q3 · 答案质量评测（LLM-as-judge）✅ 已实现 + 基线

#### 问题

现有全部指标只覆盖"意图 / 检索 / 工具 / 权限"，答案正文从未被评过。

#### 落地

- 25 条 `judge: true` case（policy/multiturn/tool/permission/chitchat），含 `expected_points` / `expected_refusal`
- 裁判：`eval/judge.py`，优先外部 `deepseek-v4-flash`（经 R0 脱敏）；输入含**参考资料 + 工具结果**
- `eval_runs` 迁移 0010：`judge_model / faithfulness_avg / points_coverage / hallucination_count / refusal_correct_rate / mode / status / progress / label`
- `POST /api/eval/run?mode=judge` 后台任务返回 `run_id`；`GET /api/quality/runs/{id}` 看进度与 judge 明细；`GET /api/quality/runs/{id}/diff?other_id=` 对比
- 复现：`uv run python scripts/run_q3_judge.py`

#### 需求

**评测子集：** case 增加 `judge: true` 标记，先选 25 条：policy 10、multiturn 5、tool 5、permission 3、chitchat 2。

**参考答案：** 每条 judge case 增加 `expected_points: [...]`——答案必须覆盖的要点（如 `["住宿标准 500 元/天", "超标需部门负责人特批"]`），2–4 条；permission / 无文档 case 用 `expected_refusal: true`。

**裁判：**
- 走 `llm_client` 的外部 provider（经 R0 脱敏），`temperature=0`；无外部 key 时允许本地模型裁判但 `eval_runs.judge_model` 必须记录，且报告标注「本地裁判，可信度低」
- 裁判输入：用户问题、参考资料片段、`expected_points`、模型答案
- 裁判输出 JSON：

| 字段 | 类型 | 说明 |
|---|---|---|
| `faithfulness` | 1–5 | 答案是否只基于参考资料 |
| `points_covered` | int / int | 覆盖了几个要点 |
| `hallucinated_claims` | list[str] | 资料中不存在的断言 |
| `refusal_correct` | bool | 仅 `expected_refusal` case：是否正确拒答且不泄漏 |
| `citation_correct` | bool | 引用的文档是否与 `expected_doc_title` 一致 |

**落库：** `eval_runs` 增加 `judge_model`、`faithfulness_avg`、`points_coverage`、`hallucination_count`、`refusal_correct_rate`；`case_results.judge` 存完整 JSON。

**运行方式：** CPU 上 7B 生成 ≈ 100 s / case，25 条 ≈ 40 min。`POST /api/eval/run?mode=judge` 改为后台任务立即返回 `run_id`，`GET /api/quality/runs/{id}` 带进度；`skip_generation` 模式不受影响。

#### 验收

1. ✅ 完整 judge 运行落库：`eval_runs` id=12（修复前）、id=13（修复后）
2. ✅ 基线数字见下表附录
3. ✅ 系统性原因分析与二次运行证明（见下）

**系统性问题（第一轮 hallu=45）：裁判输入只有制度片段，没有工具结果。**  
工具类答案里的额度/工单号/dry_run 标记被误判为编造。

**修复：**
- 裁判输入增加【工具结果】证据块；prompt 明确「工具结果优先，dry_run 单号不算编造」
- 生成侧 `_TOOL_FAIL_SECTION`：权限拒绝时禁止用制度推算他人数据；`_TOOL_SUCCESS_SECTION`：用户数据以工具结果为准

**第二轮证明（id=13）：**

| 指标 | 第一轮（id=12） | 第二轮（id=13） |
|---|---|---|
| faithfulness_avg | 3.36 | **3.80** |
| points_coverage | 0.674 | **0.791** |
| hallucination_count | 45 | **27** |
| case_004/005/006（tool） | faith=1，hallu 大量 | **faith=5，hallu=[]** |
| case_065（permission 拒答） | faith=3 | **faith=5** |

**第三轮：收紧生成提示（id=14）** — `_RAG_SYSTEM_PROMPT` 明确禁止补全资料未写明的流程/时限/SLA/赔偿。  
faithfulness 保持 3.80，hallu **27→24**；case_002 不再编造紧急补办流程。  
points_coverage 降至 0.698：模型更克制，资料没写就少答——符合「不编造」优先，长期需靠检索命中完整条款。

**残留问题（检索截断类，非本轮门禁）：**
- case_009/010/025/026：期望要点在制度全文中，但 top-k 片段未覆盖 → 模型若补全则 hallu，若拒答则 points 掉

- 根治路径：提高生成侧上下文预算、按 heading 召回整节、或 case 的 expected_points 与检索可达范围对齐

### Q6 · R5 重排（门控）

#### 门控条件

Q1 完成后，若 `distractor-topic` 子组 mrr < 0.70，进入本项；否则搁置。

#### 需求

- sidecar：`bge-reranker-v2-m3`，独立容器（FastAPI + sentence-transformers，CPU），`POST /rerank {query, passages[]} → scores[]`；docker-compose 加 `reranker` 服务，仅内网
- `retrieval_rerank_enabled`（默认 false）、`retrieval_rerank_candidates`（默认 20）、`retrieval_rerank_timeout_ms`（默认 2000）
- 流程：RRF 前 20 → 清洗（去 Markdown / URL）→ 重排 → `top_k`；超时或异常降级为 RRF 顺序，trace 记录 `rerank_applied`
- 对照：沿用 `run_quota_ab.py` 的方式，开 / 关各 3 次

#### 验收

3 次均值 mrr 提升 ≥ 0.03 且 P95 检索耗时增加 ≤ 1.5 s → 默认开启；否则保持关闭并记录数字。
