# 📄 企业智能 Agent 系统需求文档 v2.2

## 一、项目概述

### 1.1 项目背景

公司服务器资源分布广泛（混合架构：自建机房 + 云服务器），无专职运维人员；内部制度文档分散，员工查阅不便；产品线持续扩展，客服人力成本较高。

为解决以上三类问题，计划开发一套**企业智能 Agent 系统**，集运维监控、内部知识库、对外客服三大能力于一体，以 Web 产品形态交付，支持私有化部署。

---

### 1.2 整体模块架构

```
企业智能 Agent 系统
├── 模块一：运维监控 Agent      → 面向内部管理员，主动推送告警 + 人工确认执行
├── 模块二：内部知识库 Agent    → 面向全体员工，制度文档问答（RAG）
└── 模块三：客服 Agent          → 面向外部客户，产品咨询问答（RAG + API）
```

三个模块**共用**以下基础设施：
- 统一 Web 前端（React + Ant Design Pro）
- 统一后端服务（Python + FastAPI）
- 统一工作流引擎（LangGraph）
- 统一数据库（PostgreSQL）
- 统一文档解析 + 向量化 Pipeline
- 统一用户 / 权限 / 部门体系
- 统一审计日志系统

---

### 1.3 开发优先级

| **阶段** | **模块** | **理由** |
|---|---|---|
| 第一阶段 | 基础设施 + 用户权限体系 + 模块二内部知识库 + 简单前端 | 知识库是核心 RAG 能力验证，基础设施为后续模块铺路；前端只做基本聊天界面，不做复杂后台 |
| 第二阶段 | 模块一运维监控 | 在稳定的基础设施上叠加 SSH 采集、告警推送等运维能力 |
| 第三阶段 | 模块三客服 Agent | 面向外部，质量要求最高，基于前两阶段经验迭代 |

#### 第一阶段交付范围（当前阶段）

**后端（完整实现）：**
- 用户认证：JWT、bcrypt、三级角色（超级管理员 / 部门管理员 / 普通员工）
- 文档管理：上传、解析（.md / .docx / .pdf）、分块、向量化、pgvector 存储
- RAG 问答：LangGraph 工作流（意图识别 → 检索 → 生成）、SSE 流式输出、引用来源
- 审计日志：所有关键操作写入独立表
- Docker Compose 部署

**前端（简单实现，够用即可）：**
- 登录页（含错误提示：密码错误 / 账号不存在 / 账号已锁定）
- 首次登录强制修改密码引导流程
- 聊天主界面（发消息、流式显示回复、展示引用来源）
- 历史会话列表
- 个人设置（修改昵称、修改密码）
- 管理后台入口（管理员角色用户在侧边栏可见"管理后台"按钮）
- 管理后台页面：
  - 部门管理（创建 / 改名 / 删除）← 仅超级管理员
  - 账号管理（创建 / 重置密码 / 启用禁用 / 解锁）
  - 文档管理（上传 / 归档 / 重新索引 / 权限配置）
  - 审计日志查询 ← 仅超级管理员
  - 系统日志（运行日志查看，支持日期/级别/关键词过滤）← 仅超级管理员
  - 系统设置（对话记录上限配置）← 仅超级管理员

**暂不实现（留给后续阶段）：**
- 运维监控相关所有功能
- 客服 Agent 及 API Key 体系

### 工具调用系统

系统支持通过 LangGraph 工作流调用企业工具：

| 工具 | 描述 | 权限 |
|---|---|---|
| query_employee_profile | 查询员工基本信息 | 所有角色（只能查自己） |
| query_reimbursement_limit | 查询报销额度 | 所有角色（只能查自己） |
| create_it_ticket | 创建 IT 工单 | 所有角色（幂等） |

工具调用流程：
1. 意图识别 → 2. 文档检索 → 3. LLM 判断是否需要工具 → 4. 权限校验 → 5. 执行工具 → 6. 生成回答

安全约束：
- 工具调用前必须经过权限校验
- 普通员工只能查询自己的信息
- 所有工具调用写入审计日志
- 创建类工具使用幂等键防止重复执行

### 评测回归系统

系统支持 golden cases 回归评测：
- 15 条覆盖：制度问答、工具调用、闲聊、权限拒绝
- 指标：意图准确率、文档命中率、工具调用准确率、引用覆盖率
- 运行方式：POST /api/eval/run（仅超级管理员）

## 二、产品形态与 UI 结构

### 2.1 整体产品形态

系统以 **Web 应用**形式交付，包含两大界面区域：

- **用户侧**：登录页、聊天主界面、历史记录
- **管理侧**：管理后台（账号管理、文档管理、监控配置、审计日志等）

---

### 2.2 页面结构总览

```
Web 应用
├── 登录 / 登出页
│   ├── 用户名 + 密码登录
│   ├── 错误提示（密码错误 / 账号不存在 / 账号已锁定）
│   └── 首次登录 / 管理员重置密码后强制修改密码引导流程
├── 用户侧（所有登录用户）

│   │   ├── 左侧：历史会话列表
│   │   ├── 中间：对话窗口（Markdown 渲染 + 流式打字效果）
│   │   └── 右侧：来源文档引用面板（RAG 模块）
│   ├── 历史记录（查看个人历史会话，含消息记录）
│   ├── 个人设置（修改昵称、修改密码）

└── 管理侧（需管理员角色，通过侧边栏"管理后台"按钮进入）
    ├── 部门管理（创建 / 改名 / 删除）← 仅超级管理员
    ├── 账号管理
    │   ├── 超级管理员：管理员账号列表（创建 / 修改权限 / 禁用 / 解锁）
    │   └── 部门管理员：本部门员工列表（创建 / 修改权限 / 禁用 / 解锁）
    ├── 文档管理（上传 / 归档 / 重新索引 / 权限配置）
    ├── 审计日志（所有操作记录）                    ← 仅超级管理员
    ├── 系统日志（运行日志查看，支持级别/关键词过滤）← 仅超级管理员
    └── 系统设置（对话记录上限配置）                ← 仅超级管理员
```

### 2.3 角色与权限体系

系统采用**三级角色模型**：超级管理员 → 部门管理员 → 普通员工。

#### 角色权限总览

| **角色** | **权限范围** |
|---|---|
| 超级管理员 | 全局所有功能；管理所有部门管理员账号；访问所有资源（文档、对话记录、审计日志）；系统配置 |
| 部门管理员 | 管理本部门员工账号；管理本部门文档及权限；查看本部门对话日志；不可访问运维监控模块 |
| 普通员工 | 使用聊天功能；查看个人历史对话记录；修改个人昵称和密码 |

#### 超级管理员

- 系统初始化时内置唯一超级管理员账号，**首次登录强制修改初始密码**
- 超级管理员账号**唯一**，不支持创建多个
- 职责：创建 / 修改权限 / 禁用 / 账号转移（针对各部门管理员账号）
- 可访问系统内**所有资源**，包括所有部门文档、所有用户对话记录、审计日志
- 账号转移范围：**文档归属 + 权限配置**（适用于管理员离职场景）

#### 部门管理员

- 由超级管理员创建，创建时需填写以下信息：

| **字段** | **是否必填** | **说明** |
|---|---|---|
| 所属部门 | ✅ 必填 | 决定其管理范围 |
| 姓名 | ✅ 必填 | 用于显示和审计日志 |
| 管理权限范围 | ✅ 必填 | 可上传文档 / 可查看对话日志（可组合勾选） |
| 邮箱 | ⬜ 选填 | 预留字段，后续支持通知和密码找回 |
| 备注 | ⬜ 选填 | 如"技术部负责人" |

- 创建后系统**自动生成随机密码**，支持一键复制，**密码仅展示一次**，关闭后不可再查
- 管理员首次登录**强制修改密码**
- 每个部门可有多名部门管理员
- 部门管理员**不可跨部门操作**，不可访问运维监控模块

#### 普通员工

- 由所属部门的部门管理员创建，创建时需填写：

| **字段** | **是否必填** | **说明** |
|---|---|---|
| 姓名 | ✅ 必填 | 用于显示和审计日志 |
| 所属部门 | ✅ 必填 | 自动继承部门管理员所在部门 |
| 资源访问权限 | ✅ 必填 | 可访问哪些文档权限组（见文档权限章节） |
| 备注 | ⬜ 选填 | — |

- 创建后系统**自动生成随机密码**，支持一键复制，**密码仅展示一次**
- 首次登录**强制修改密码**
- 账号转移范围：**文档归属 + 权限配置**（适用于员工离职场景，由部门管理员操作）

---

### 2.4 用户名规范

- 用户名格式：**姓名全拼**，全小写，例如 `zhangsan`
- 重名时系统自动追加数字后缀，例如 `zhangsan01`、`zhangsan02`
- 用户名创建后**不可修改**，作为系统唯一登录凭证和审计标识
- 用户可修改**昵称**（显示名），昵称不影响登录和审计
- 用户名由系统在创建账号时根据填写的姓名自动生成，管理员可在生成后手动调整

---

### 2.5 登录与会话管理

- 登录方式：用户名 + 密码（系统自建账号）
- 密码存储：bcrypt 哈希，禁止明文存储
- 登录态：JWT Token，支持过期刷新
- 登录失败超过 N 次锁定账号（次数可配置，默认 5 次），锁定后提示联系管理员
- 支持强制登出（管理员可踢出指定用户）
- 以下场景强制要求修改密码后才可进入系统：
  - 首次登录
  - 管理员重置密码后

---

### 2.6 对话历史记录设计

#### 内部用户（员工 + 管理员）

所有登录用户均可查看**个人历史对话记录**，系统按以下规则管理存储上限：

| **配置项** | **默认值** | **说明** |
|---|---|---|
| 每用户最大会话数 | 200 个 | 超出后最旧会话自动转为归档状态 |
| 每会话最大消息数 | 500 条 | 超出后截断最早消息 |
| 归档数据保留时长 | 180 天 | 到期后物理删除，不可恢复 |

- 归档会话用户不可见，但超级管理员审计时仍可查询
- 以上配置项由超级管理员在系统设置中维护

#### 外部客户（客服 API 访问者）

外部客户通过 API Key 访问，无系统账号，对话模型与内部用户不同：

- 每个外部用户对应唯一 `visitor_id`，对应**一条连续对话时间线**，无多会话概念
- `visitor_id` 生成规则：兼容两种模式
  - 调用方传入：接入方有自己的用户体系时使用
  - 系统自动分配：调用方未传入时自动生成并返回，由调用方存储后续携带
- `visitor_id` 与 API Key 绑定，不同产品线数据天然隔离
- 对话记录保留 **180 天**，到期后物理删除
- 原始对话数据由**定时分析程序**每日处理（见模块三 6.7 节）

### 3.2 LLM 提供商配置

系统支持多种 LLM 提供商，通过环境变量配置选择：

| **配置项** | **环境变量** | **默认值** | **说明** |
|---|---|---|---|
| 提供商选择 | `LLM_PROVIDER` | `ollama` | `ollama` 或 `openai_compatible` |
| Ollama 地址 | `OLLAMA_BASE_URL` | `http://ollama:11434` | Ollama 服务地址 |
| Ollama 聊天模型 | `OLLAMA_CHAT_MODEL` | `qwen2.5:7b` | 本地聊天模型 |
| Ollama Embedding | `OLLAMA_EMBED_MODEL` | `nomic-embed-text` | 向量化模型（始终使用 Ollama） |
| OpenAI 兼容 API Key | `OPENAI_API_KEY` | 空 | DeepSeek、Qwen-Max 等外部 API 密钥 |
| OpenAI 兼容 URL | `OPENAI_BASE_URL` | `https://api.deepseek.com/v1` | API 基础 URL |
| OpenAI 兼容模型 | `OPENAI_MODEL` | `deepseek-chat` | 模型名称 |

**支持的 LLM 提供商：**
- **Ollama 本地部署**：Qwen2.5、Llama3 等开源模型
- **OpenAI 兼容 API**：DeepSeek、Qwen-Max、vLLM、OpenAI 等

**关键约束：**
- Embedding 模型始终使用 Ollama 本地部署，不支持外部 API
- 切换 LLM 提供商需重启服务生效
- 使用外部 API 时，敏感信息需经脱敏处理后方可发送

### 3.3 模型分档策略

系统根据**用户角色**和**任务类型**动态选择调用的模型，平衡能力与成本：

| **档次** | **适用场景** | **模型示例** |
|---|---|---|
| 🔴 高级模型（外部 API） | 管理员使用 / 运维诊断分析 / 复杂推理任务 | DeepSeek-V3、Qwen-Max 等 |
| 🟡 标准模型（本地部署） | 普通员工知识库问答 / 客服标准问答 | Qwen2.5-7B、Llama3-8B 等本地模型 |
| 🟢 轻量模型（本地部署） | 意图识别 / 关键词提取 / 简单分类 | 小参数量模型或规则引擎 |

**模型路由规则：**
- 用户角色为管理员 → 优先路由至高级模型
- 普通问答且无敏感操作 → 路由至本地标准模型
- 敏感信息脱敏处理后方可发送至外部 API 模型（见安全章节）
- 模型配置由超级管理员在系统设置中维护，支持热切换

---

### 3.3 SSE 流式输出规范

所有对话接口统一采用 **SSE（Server-Sent Events）** 实现流式输出：

```
GET/POST /api/chat/stream

响应格式（text/event-stream）：
data: {"type": "token", "content": "支持"}
data: {"type": "token", "content": "OTA"}
data: {"type": "token", "content": "升级"}
data: {"type": "sources", "content": [...]}
data: {"type": "done", "content": ""}
```

- 前端逐 token 渲染，实现打字机效果
- `sources` 事件在流结束前推送，展示引用来源
- `done` 事件标志本次回答结束
- 异常时推送 `{"type": "error", "content": "错误信息"}`

## 四、模块一：运维监控 Agent

### 4.1 模块背景与目标

公司目前拥有多台服务器（数量动态增长），部署环境为**混合架构**（自建机房 + 云服务器），运行服务种类繁多，包括但不限于：Web 服务、数据库、MQTT Broker、GitLab、OTA 服务器、后端工具服务等。

公司**无专职运维岗位**，因此需要一个自动化监控 Agent，代替人工持续巡检，在发现异常时主动告警并提供诊断建议，所有操作需人工确认并全程审计。

**访问权限：仅超级管理员可访问运维监控模块的所有功能。**

---

### 4.2 数据采集方式

- 采用 **SSH 免密登录**方式连接被监控服务器
- 系统服务器需提前配置 SSH 公钥至各目标服务器
- 采集通过执行远程命令实现（如 `top`、`df`、`ps`、`tail` 等）
- 采集间隔默认 **60 秒**，管理员可按服务器单独配置
- SSH 连接异常本身视为告警事件（服务器失联）

**SSH 配置项（每台服务器）：**
- 目标 IP / 域名
- SSH 端口（默认 22）
- 登录用户名
- 私钥路径（系统统一管理，不对外暴露）

---

### 4.3 监控能力范围

#### 基础资源监控（所有服务器统一采集）
- CPU 使用率
- 内存使用率
- 磁盘使用率（含各挂载分区）

#### 进程存活监控（按服务器独立配置）
- 监控对象为**管理员手动配置的重点进程**
- 每台服务器的重点进程列表可在管理后台独立维护
- 检测进程是否存活，若进程意外退出则立即触发告警

#### 日志异常监控（针对重点进程）
- 对已配置的重点进程，同步监控其日志输出
- 管理员可为每个进程配置**异常关键词列表**（如 `ERROR`、`OOM`、`connection refused`、`panic`）
- 日志中出现匹配关键词时触发告警，附带上下文（前后各 10 行）

---

### 4.4 服务器管理机制

系统支持**动态添加/删除服务器**，无需重新部署。每台服务器配置项：

- 服务器名称 / 标签（如：生产数据库、GitLab 服务器）
- 所属环境（机房 / 云，可扩展）
- SSH 连接配置（IP、端口、用户名、私钥）
- 重点进程列表（进程名 + 日志路径 + 异常关键词列表）
- 各监控指标的告警阈值（可单独设置，覆盖全局默认值）

---

### 4.5 告警机制

#### 告警触发条件

| **监控项** | **默认告警阈值** |
|---|---|
| CPU 使用率 | 持续 5 分钟 > 85% |
| 内存使用率 | > 90% |
| 磁盘使用率 | > 85% |
| 进程存活 | 进程不存在即告警 |
| 日志关键词 | 匹配即告警 |
| SSH 连接失败 | 连续 3 次失败即告警 |

#### 告警推送方式
- **当前阶段**：推送至 Web 管理界面告警中心（站内消息 + 醒目角标），仅超级管理员可见
- **后续扩展**：对接企业微信群机器人，采用 **WebSocket 长连接**方式保持实时推送能力

#### 告警内容规范
每条告警包含：
- 服务器名称 + IP
- 异常类型（资源超限 / 进程宕机 / 日志异常 / 服务器失联）
- 具体数值或异常日志片段
- 发生时间
- Agent 诊断建议
- 可执行操作按钮（需人工确认）

---

### 4.6 诊断建议能力

Agent 触发告警时，结合异常类型自动生成诊断建议：

- **CPU 高负载** → 列出 Top 进程，建议排查死循环或异常任务
- **内存不足** → 提示可能泄漏进程，建议重启或扩容
- **磁盘告警** → 分析最大占用目录/文件，建议清理日志或扩容
- **进程宕机** → 展示最近日志片段，建议检查启动配置或依赖服务
- **日志关键词** → 展示上下文日志，给出初步原因推断

---

### 4.7 服务操作能力

Agent 具备通过 SSH 执行服务启停操作的能力，**所有操作必须人工确认，全程审计**。

#### 支持的操作类型

| **操作** | **示例命令** | **风险等级** |
|---|---|---|
| 启动服务 | `systemctl start nginx` | 🟡 中 |
| 停止服务 | `systemctl stop nginx` | 🔴 高 |
| 重启服务 | `systemctl restart nginx` | 🔴 高 |
| 查看服务状态 | `systemctl status nginx` | 🟢 低（只读） |
| 查看实时日志 | `journalctl -f -u nginx` | 🟢 低（只读） |

#### 操作执行流程
```
Agent 给出建议操作
    ↓
Web 界面展示操作详情（服务器、命令、预期影响）
    ↓
管理员点击"确认执行"→ 二次弹窗确认
    ↓
系统通过 SSH 执行命令
    ↓
实时回显执行结果
    ↓
写入审计日志（操作人、时间、命令、结果）
```

#### 操作权限限制
- 仅**超级管理员**可执行所有运维操作（含高风险停止/重启）
- 部门管理员及普通员工不可访问运维操作功能
- 禁止执行预设白名单之外的命令（防止命令注入）
- 命令白名单由超级管理员在系统设置中维护

---

### 4.8 企业微信机器人集成（后续阶段）

- 采用 **WebSocket 长连接**方式接入企业微信机器人
- 告警触发时实时推送消息至指定企业微信群
- 推送内容包含：告警摘要 + 诊断建议 + Web 端处理链接
- 连接断开时自动重连，重连失败降级为 Web 站内告警

## 五、模块二：内部知识库 Agent

### 5.1 模块背景与目标

公司存有多份内部制度文档（出差规范、报销规范、行为准则等），员工需自行翻找文件，效率低且容易找到旧版本。

本模块将文档构建为**企业内部知识库**，员工通过自然语言提问即可获得准确答案并附带原文出处。

---

### 5.2 支持的文档格式

| **格式** | **说明** |
|---|---|
| `.docx` / `.doc` | Word 文档 |
| `.md` | Markdown 文档 |
| `.pdf` | PDF 文档（扫描件 OCR 支持列为后续扩展） |

- 文档总量当前预计 100 份以内，系统设计支持后续扩展
- 单文件建议上限 50MB

---

### 5.3 文档管理机制

#### 上传与更新
- 管理员手动上传，无需自动同步
- 支持覆盖更新，旧版本自动归档（保留历史，不直接删除）
- 上传后自动执行：**文档解析 → 分块 → 向量化 → 入库**
- 处理完成前该文档不参与检索，处理状态实时展示

#### 文档元信息
- 文档名称
- 所属分类（管理员自定义，如：行政制度 / 财务规范 / HR 政策）
- 可见权限（见 5.4）
- 上传时间 / 最后更新时间
- 版本号（可选，手动填写）

---

### 5.4 文档权限控制体系

系统采用**四级权限模型**，由上传文档的部门管理员在上传时配置：

| **权限级别** | **说明** | **示例场景** |
|---|---|---|
| 🌐 全体共享 | 所有登录用户均可访问（含客服部门） | 出差规范、报销流程、假期制度 |
| 🏢 非客服共享 | 除客服部门外所有部门成员可访问 | 内部技术规范、管理制度 |
| 👥 本部门共享 | 仅本部门成员可访问 | 技术部开发规范、销售话术手册 |
| 👤 本部门指定人员 | 仅本部门内指定成员可访问 | HR 专属薪资政策、管理层决策文档 |

- 一份文档对应一个权限级别，"本部门指定人员"可额外勾选具体成员
- 检索时自动过滤为当前用户有权访问的文档
- 无权文档不参与召回，且**不透露其存在**
- 超级管理员可访问所有权限级别的文档

---

### 5.5 问答能力规范

- 自然语言提问，支持多轮对话追问
- 回答包含：直接答案 + 原文依据（文档名 + 段落）+ 置信提示
- 知识库无内容时明确告知，不编造
- 超出文档范围的问题礼貌拒答
- 文档内容矛盾时同时展示，提示以最新版本为准
- 全部回答通过 **SSE 流式输出**

---

### 5.6 管理员后台能力

- 文档上传 / 删除 / 归档 / 版本管理（部门管理员仅可管理本部门文档）
- 权限配置（文档维度 + 用户维度双向管理）
- 查询日志（员工问了什么、命中了哪份文档）——部门管理员仅可查看本部门员工的日志
- 文档处理状态查看（解析中 / 已就绪 / 解析失败）

---

## 六、模块三：客服 Agent

### 6.1 模块背景与目标

公司产品线覆盖多类产品，客户咨询量持续增长。本模块构建**对外客服 Agent**，基于产品说明书、开发文档、售后流程等资料自动回答客户咨询，降低人工客服介入频率。

系统以**标准 Web API 接口**形式交付，方便后续灵活接入官网、小程序、APP 或第三方客服平台。

---

### 6.2 权限与账号处理

- 客服 Agent 在系统中作为**独立的"客服部门"**存在
- 客服知识库文档归属于客服部门，由客服部门管理员维护
- 客服部门管理员由超级管理员创建，与其他部门管理员创建流程一致
- 外部客户通过 API Key 访问，**不需要系统账号**
- 不同产品线对应不同的 API Key，实现隔离管理
- 客服部门成员**不可访问**其他部门的"非客服共享"及以下权限级别的文档

---

### 6.3 知识库内容范围

#### 支持文档类型
- 产品说明书（Word / PDF）
- 开发文档（Word / PDF）
- 售后流程与常见问题文档（Word / PDF）

#### 多产品线管理
- 按产品线维度组织知识库，每条产品线独立管理文档
- 客户提问时优先在对应产品线知识库检索
- 产品线不明确时跨全库检索并标注来源

---

### 6.4 问答与意图识别

| **意图类型** | **示例** | **处理方式** |
|---|---|---|
| 产品功能咨询 | "这个设备支持哪些通信协议？" | RAG 检索产品说明书 |
| 开发集成问题 | "API 怎么鉴权？" | RAG 检索开发文档 |
| 售后问题 | "设备故障了怎么处理？" | RAG 检索售后文档 |
| 超出范围问题 | "你们股票怎么样？" | 礼貌拒答，引导回产品话题 |

- 支持多轮对话，SSE 流式输出
- 回答标注来源文档名称 + 章节
- 置信度低时主动提示建议核实

---

### 6.5 人工兜底机制

以下情况主动告知联系人工客服：
- 知识库无相关内容
- 涉及订单、账号、退换货等需操作权限事项
- 客户明确要求转人工
- 同一问题连续追问 2 次仍未解决

人工客服联系方式由管理员后台配置，Agent 动态读取。

---

### 6.6 API 接口规范（SSE 版本）

#### 核心接口

| **接口** | **方法** | **说明** |
|---|---|---|
| `POST /api/customer/chat/stream` | POST | 发送消息，SSE 流式返回回复，支持传入 `visitor_id` |
| `GET /api/customer/chat/history` | GET | 获取指定 `visitor_id` 的对话历史 |
| `POST /api/customer/session/new` | POST | 创建新会话，未传入 `visitor_id` 时系统自动分配并返回 |

#### SSE 响应格式
```
Content-Type: text/event-stream

data: {"type": "token", "content": "支持"}
data: {"type": "token", "content": "OTA升级"}
data: {"type": "sources", "content": [{"doc_name": "产品A说明书.pdf", "section": "第4章"}]}
data: {"type": "suggest_human", "value": false}
data: {"type": "done"}
```

#### 鉴权
- API Key 鉴权，Header 中携带 `X-API-Key`
- 支持多 API Key，可独立启用/禁用，对应不同产品线或接入方
- `visitor_id` 与 API Key 绑定，跨 API Key 的 `visitor_id` 不互通

---

### 6.7 客服对话分析（定时任务）

系统内置轻量级定时分析程序，对客服对话数据进行周期性统计，辅助知识库运营。

#### 分析任务规范

| **配置项** | **默认值** | **说明** |
|---|---|---|
| 执行频率 | 每天凌晨一次 | 低峰期执行，可配置 |
| 分析时间窗口 | 最近 30 天（滚动） | 可配置 |
| 分析结果存储 | 独立统计汇总表 | 不修改原始对话数据 |

#### 分析内容

| **分析类型** | **说明** |
|---|---|
| 高频问题关键词 Top 20 | 基于词频统计，按产品线分组 |
| 未命中问题列表 | 触发人工兜底的问题，直接从标记字段读取 |
| 各产品线对话量统计 | 按日/周/月维度汇总 |

- 分析结果在管理后台**客服分析报表**页展示
- 可查看角色：客服部门管理员 + 超级管理员
- 后续扩展：向量相似度聚类、满意度分析（等用户量增长后迭代）

#### 数据保留规则
- 原始对话记录保留 **180 天**，到期后物理删除
- 统计汇总结果**长期保留**，不随原始数据删除

## 七、安全设计

### 7.1 全局审计日志

**所有以下操作必须写入审计日志，不可删除：**

| **操作类型** | **记录内容** |
|---|---|
| 用户登录 / 登出 | 用户、时间、IP、成功/失败 |
| 账号管理操作 | 操作人、被操作账号、变更内容（含账号转移记录） |
| 文档上传 / 删除 / 权限变更 | 操作人、文档名、变更内容、时间 |
| 运维操作执行 | 操作人、目标服务器、执行命令、执行结果、时间 |
| 模型配置变更 | 操作人、变更前后配置 |
| API Key 创建 / 禁用 | 操作人、Key 标识、时间 |
| 密码重置 | 操作人、被操作账号、时间 |

- 审计日志存入 PostgreSQL 独立表，**仅超级管理员可查看**
- 日志不可通过系统界面删除（物理保留）

---

### 7.2 日志系统设计

采用 **loguru** 作为日志系统，支持以下特性：

#### 日志文件管理
- **按天轮转**：每天生成一个日志文件，命名格式 `workpilot_{YYYY-MM-DD}.log`
- **自动删除**：可配置保留天数，默认 7 天自动清理过期日志
- **存储位置**：开发模式存于 `backend/logs/`，Docker 部署通过卷挂载到宿主机

#### 日志等级
| **等级** | **用途** |
|---|---|
| DEBUG | 调试信息，仅开发模式显示 |
| INFO | 一般信息，记录系统运行状态 |
| WARNING | 警告信息，不影响运行但需关注 |
| ERROR | 错误信息，系统异常但可继续运行 |
| CRITICAL | 严重错误，系统无法继续运行 |

#### 请求追踪
- 为每个请求生成唯一 `request_id`（UUID 前 8 位）
- 通过请求头 `X-Request-ID` 传递
- 日志格式包含 `request_id` 和 `user_id`，便于追踪请求链路

#### 日志格式
```
{time:YYYY-MM-DD HH:mm:ss.SSS} | {level: <8} | {name}:{function}:{line} | req_id={request_id} | user_id={user_id} | {message}
```

#### 业务关键操作日志
以下操作必须记录到日志：
- 用户登录/登出（成功与失败）
- 密码修改/重置
- 用户创建/修改/删除
- 文档上传/修改/删除/重新索引
- 部门创建/修改/删除
- 系统配置修改

---

### 7.3 输入验证规范

采用 **Pydantic Schema** 加强输入验证：

#### 密码策略
- 最小长度：8 位
- 复杂度要求：必须包含大写字母、小写字母、数字
- 新密码不能与当前密码相同

#### 用户名规范
- 格式：姓名全拼，全小写（如 `zhangsan`）
- 重名时自动追加数字后缀（如 `zhangsan01`）
- 创建后不可修改

#### 员工编号规范
- 格式：`{部门代码}{3位数字}`（如 `HR001`、`RD023`）
- 由系统自动推荐，管理员可手动调整

#### XSS 防护
- 昵称、姓名等文本字段禁止包含 `<>"'&` 字符
- 邮箱格式校验
- 备注字段长度限制（500 字符）

#### 文件上传验证
- 文件类型：仅允许 `.pdf`、`.docx`、`.md`
- 文件大小：最大 200 MB（可配置）

---

### 7.4 敏感信息脱敏

**调用外部 LLM API 前，必须对以下信息进行脱敏处理：**

| **敏感信息类型** | **脱敏方式** |
|---|---|
| 姓名 | 替换为 `[姓名]` |
| 手机号 | 替换为 `[手机号]` |
| 身份证号 | 替换为 `[证件号]` |
| IP 地址 | 替换为 `[IP地址]` |
| 服务器密码 / 密钥 | 替换为 `[凭证]` |
| 邮箱地址 | 替换为 `[邮箱]` |

- 脱敏在 LangGraph 工作流的**前置节点**中统一处理
- 本地模型不需要脱敏（数据不出内网）
- 脱敏规则由超级管理员可配置扩展

---

### 7.5 其他安全要求

- 所有接口需鉴权，禁止匿名访问（客服 API 用 API Key）
- 密码 bcrypt 哈希存储
- SSH 私钥加密存储，不对外暴露
- 运维命令执行严格白名单，防止命令注入
- 权限校验在**服务端**执行，前端仅做展示控制
- HTTPS 部署（生产环境强制）
- 账号锁定后须由上级管理员手动解锁（普通员工由部门管理员解锁，部门管理员由超级管理员解锁）

## 八、非功能性需求

### 8.1 性能要求
- 知识库问答首 token 响应时间：**≤ 3 秒**（P95）
- 监控数据采集间隔：可配置，默认 60 秒
- 告警触发到 Web 推送延迟：**≤ 30 秒**
- 并发用户数：支持 **50 并发**（初期，可水平扩展）

### 8.2 可靠性要求
- 监控 Agent 高可用，自身故障需有自检告警
- PostgreSQL 支持定期自动备份
- 服务异常时提供降级响应，不直接崩溃

### 8.3 可扩展性要求
- 服务器数量动态增长，无需重新部署
- 文档数量、产品线增长不影响稳定性
- 告警推送渠道预留扩展接口
- 模型支持热切换，不需要重启服务

### 8.4 部署要求
- 私有化部署，数据不出公司内网
- Docker + Docker Compose 一键部署
- 提供环境变量配置文件（`.env`），敏感配置不写入代码
