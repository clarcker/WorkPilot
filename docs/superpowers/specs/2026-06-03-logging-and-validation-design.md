# WorkPilot v2 日志系统与输入验证设计文档

## 1. 概述

本文档描述了WorkPilot v2后端系统的日志系统和输入验证加强方案的设计。

### 1.1 设计目标

1. **日志系统**：建立完整的日志系统，支持按天轮转、自动删除过期日志、请求追踪格式、分等级日志
2. **输入验证**：加强Pydantic Schema验证，增加边界条件验证，提高系统健壮性
3. **配置管理**：统一配置文件，最多2个文件（.env存放密钥，config.py存放可公开配置）

### 1.2 设计原则

1. **简单性**：使用成熟的技术栈，避免过度设计
2. **可配置性**：关键参数可通过配置文件调整
3. **性能优先**：业务关键信息和系统重要报错信息不得过滤，不重要的业务信息可适当减少日志内容
4. **开发友好**：开发模式下显示所有信息，方便排查问题

## 2. 日志系统设计

### 2.1 技术选型

使用loguru库作为日志系统，主要优点：
- 功能强大：自动轮转、压缩、删除等
- 配置简单：API友好，易于使用
- 性能优秀：异步日志记录，对性能影响小

### 2.2 日志文件管理

1. **日志文件轮转**：按天轮转，每天生成一个日志文件
2. **日志文件命名**：workpilot_{time:YYYY-MM-DD}.log
3. **日志文件存储位置**：
   - 开发模式：backend/logs/目录
   - 稳定模式（Docker）：通过Docker卷挂载到宿主机
4. **日志文件过期**：可配置过期天数，默认7天自动删除

### 2.3 日志等级

1. **DEBUG**：调试信息，开发模式下显示
2. **INFO**：一般信息，记录系统运行状态
3. **WARNING**：警告信息，不影响系统运行但需要关注
4. **ERROR**：错误信息，系统出现异常但可以继续运行
5. **CRITICAL**：严重错误，系统无法继续运行

### 2.4 日志格式

请求追踪格式：
{time:YYYY-MM-DD HH:mm:ss.SSS} | {level: <8} | {name}:{function}:{line} | {extra[request_id]} | {extra[user_id]} | {message}

### 2.5 日志输出目标

1. **文件输出**：所有日志输出到文件
2. **控制台输出**：开发模式下输出到控制台，稳定模式下只输出WARNING及以上
3. **可配置**：通过配置文件控制输出目标

### 2.6 请求追踪

1. **请求ID生成**：为每个请求生成唯一请求ID（UUID）
2. **请求ID传递**：通过请求头传递（如X-Request-ID）
3. **请求ID记录**：记录到日志中，便于追踪请求链路

### 2.7 业务关键操作日志

必须记录的业务关键操作：
1. 用户登录/登出
2. 密码修改/重置
3. 用户创建/修改/删除
4. 文档上传/修改/删除
5. 部门创建/修改/删除
6. 系统配置修改

## 3. 输入验证设计

### 3.1 Schema验证加强

1. **邮箱格式验证**：使用Pydantic的EmailStr类型
2. **手机号格式验证**：使用正则表达式验证中国大陆手机号
3. **密码强度验证**：
   - 最小长度：8位
   - 复杂度要求：至少包含大小写字母和数字
4. **用户名格式验证**：字母开头，允许字母数字下划线，长度3-20
5. **员工编号格式验证**：部门代码+3位数字，如HR001

### 3.2 边界条件验证

1. **空值检查**：必填字段不能为空
2. **字符串长度检查**：最小/最大长度限制
3. **数值范围检查**：如分页参数page>=1，page_size>=1且<=100
4. **特殊字符过滤**：防止XSS、SQL注入
5. **文件类型验证**：只允许上传pdf、docx、md文件
6. **文件大小验证**：最大200MB（可配置）

### 3.3 业务逻辑验证

1. **部门存在性验证**：创建用户时验证部门是否存在
2. **用户存在性验证**：修改用户信息时验证用户是否存在
3. **用户权限验证**：验证用户是否有权限执行操作
4. **唯一性约束验证**：用户名、员工编号等唯一性验证

### 3.4 错误处理

1. **统一错误响应格式**：
```json
{
  "code": 40001,
  "data": null,
  "message": "错误信息"
}
```
2. **详细的错误信息**：便于调试，但不暴露敏感信息
3. **错误日志记录**：所有错误都记录到日志系统

## 4. 配置管理设计

### 4.1 配置文件结构

1. **.env文件**：存放密钥等隐私数据
   - JWT密钥
   - 数据库密码
   - API密钥
   - 其他敏感配置

2. **config.py文件**：存放可公开配置
   - 日志等级
   - 文件大小限制
   - 过期天数
   - 其他非敏感配置

### 4.2 日志相关配置

```python
# config.py
LOG_LEVEL = "DEBUG"  # DEBUG, INFO, WARNING, ERROR, CRITICAL
LOG_ROTATION = "1 day"  # 日志轮转周期
LOG_RETENTION = "7 days"  # 日志保留时间
LOG_CONSOLE = True  # 是否输出到控制台
```

### 4.3 输入验证相关配置

```python
# config.py
MAX_FILE_SIZE_MB = 200  # 最大文件大小
ALLOWED_FILE_TYPES = ["pdf", "docx", "md"]  # 允许的文件类型
PASSWORD_MIN_LENGTH = 8  # 密码最小长度
```

### 4.4 配置加载

1. **使用pydantic-settings加载.env文件**
2. **使用Python配置类加载config.py配置**
3. **提供默认值**：确保配置缺失时系统仍能运行

## 6. 预期效果

### 6.1 日志系统效果

1. **开发模式**：所有日志输出到控制台和文件，方便调试
2. **稳定模式**：只记录关键信息，减少日志文件大小
3. **请求追踪**：可以追踪每个请求的完整链路
4. **自动清理**：过期日志自动删除，不会占用过多磁盘空间

### 6.2 输入验证效果

1. **减少错误**：通过输入验证减少系统错误
2. **提高安全性**：防止XSS、SQL注入等攻击
3. **改善用户体验**：提供更友好的错误提示
4. **系统健壮性**：提高系统对异常输入的处理能力

## 7. 风险评估

### 7.1 技术风险

1. **loguru库兼容性**：需要确保与现有代码兼容
2. **性能影响**：日志记录可能对性能有一定影响
3. **配置复杂性**：配置项过多可能增加维护难度

### 7.2 缓解措施

1. **充分测试**：在开发环境充分测试
2. **性能监控**：监控日志系统对性能的影响
3. **文档完善**：完善配置文档，降低维护难度
